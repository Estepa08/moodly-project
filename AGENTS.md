# Moodly Project

## Язык

Все агенты должны предоставлять информацию только на русском языке. Это касается всех ответов, комментариев к коду, документации и любых других текстовых сообщений.

## Рабочий процесс Git (ветки и деплой)

В репозитории **одна постоянная ветка**: `main`.

- **`main`** — единственная постоянная ветка: в неё сливаются все фичи, и именно `main` является прод-релизной веткой. Push в `main` триггерит автодеплой на DockHost.

Процесс:

1. Фичи разрабатываются в отдельных ветках → **PR в `main`**.
2. **Релиз в прод:** merge PR в `main` → автодеплой на DockHost.
3. `main` защищена на GitHub (изменения только через PR, force-push запрещён). Не пытаться пушить в `main` напрямую — всегда через PR.
4. `russia` (прод-релизная ветка) **больше не используется** и удалена — отдельный релизный PR `main → russia` не делается.

Правила:

- Delete ветки после merge.
- Не создавать новых постоянных веток. Временные фиче-ветки удалять после мержа в `main`.
- Не форсить-пушить в защищённые ветки; при расхождении контента выравнивать через PR.

## Навигация по коду через графы

Чтобы не читать/грепать `backend/src` и `frontend/src` целиком на каждый запрос, в репозитории есть лёгкий слой навигации:

- `graph/backend-graph.json`, `graph/frontend-graph.json`, `graph/shared-graph.json` — графы зависимостей (кто что импортирует), генерируются через `make graph` (использует `madge`). Коммитятся в репозиторий.
- `scripts/graph-query.mjs` — CLI без зависимостей для запросов по графу: `dependents` (кто импортирует файл) и `imports` (что импортирует файл сам).
- `api-contract/*.tsp` — источник истины по API-контракту (TypeSpec).
- `backend/prisma/schema.prisma` — источник истины по схеме БД.

Правила для агента:

1. **Вопрос «что зависит от X» / «что импортирует X»** → сначала вызвать `graph-query.mjs` (напрямую или через `make graph-query Q=<имя> MODE=<dependents|imports> PKG=<backend|frontend|shared>`), а не grep/glob по всему дереву.
   ```
   node scripts/graph-query.mjs graph/backend-graph.json creature dependents
   node scripts/graph-query.mjs graph/backend-graph.json creature imports
   ```
2. **Вопрос по API** (эндпоинты, схемы запросов/ответов) → читать `api-contract/*.tsp`, не перебирать файлы в `backend/src/routes`.
3. **Вопрос по схеме БД** (модели, связи, поля) → читать `backend/prisma/schema.prisma` целиком, не искать по коду.
4. **Полное сканирование `src` через поиск по всему дереву запрещено как первый шаг.** Допустимо только если граф и точечный запрос через `graph-query.mjs` не дали ответа (например, файл ещё не закоммичен или граф устарел) — и в этом случае агент обязан явно обосновать в ответе, почему потребовалось полное сканирование.
5. Если менялись файлы в `backend/src` или `frontend/src`, а `graph/*.json` не пересоздавались — перед завершением задачи выполнить `make graph`, чтобы граф не устаревал (это также проверяется предупреждением в `.husky/pre-push`).

## Стек

- Backend: Fastify + TypeScript (Node 22), Prisma ORM
- Frontend: React + TypeScript + Vite (PWA, i18n, vitest)
- Database: PostgreSQL + Prisma
- Shared: `shared/` — пакет `@moodly/shared` (типы/утилиты для backend и frontend)
- API-контракт: `api-contract/` — TypeSpec → OpenAPI (источник истины)
- Infrastructure: Docker (монолитный `Dockerfile`: frontend + backend + Caddy), деплой на RU-хостинге DockHost (ветка `main`), CI/CD — GitHub Actions (`ci.yml`, `e2e.yml`)

## Скиллы

При работе с фронтендом применять установленные скиллы:

- `react-vite-best-practices` — оптимизация Vite-сборки (code-splitting, ассеты, dev-производительность, анализ бандла)
- `vercel-react-best-practices` — производительность React-компонентов
- `design-guide` — дизайн-система Paperclip UI для UI-компонентов

## Визуальные элементы

Перед реализацией любого визуального компонента (React-компонент, UI-элемент, лейаут, анимация, схема расположения блоков) агент **обязан** нарисовать SVG-макет с размерами, отступами и расположением элементов — **на этапе планирования, до написания кода**.

Последовательность:

1. **Планирование** — агент рисует SVG-макет, сохраняет в `docs/` и открывает в браузере для визуальной оценки
2. **Обсуждение** — пользователь смотрит макет и вносит правки; при необходимости агент рисует новые версии макета
3. **Утверждение** — только после того, как макет утверждён, агент приступает к реализации компонента в коде

Исключение — только если макет уже существует или пользователь явно отказался.

## Фиксация утверждённых планов

После утверждения пользователем плана задачи агент **обязан** сохранить его в `docs/plans/<название>.md`.

**Зачем:** чтобы при работе со следующей задачей понимать контекст уже реализованного — что сделано, как двигались и на чём остановились.

Структура плана:

- Цель задачи
- Шаги реализации
- Статус (`в работе` / `готово`)
- Что уже реализовано
- Где остановились / что дальше

Перед началом новой задачи изучить `docs/plans/` для контекста. Обновлять файл по мере продвижения.

## Отчёт об изменениях кода

После завершения любого рефакторинга, переписывания компонента или массового изменения кода агент **обязан** предоставить отчёт об изменении объёма кода:

- количество добавленных строк
- количество удалённых строк
- чистый результат (дельту)

Для подсчёта использовать `git diff --stat` или `wc -l` по изменённым файлам. Отчёт выводится текстом без комментариев.

## Реестр реализованных решений и роадмэп

Реализованные решения фиксируются, чтобы на их основе позже составить роадмэп проекта (в т.ч. для портфолио).

**Файл:** `docs/decisions/decisions.md` — единый реестр принятых и реализованных решений. Если файла нет — создать.

После реализации каждого значимого решения (архитектура, деплой, фича, миграция БД, интеграция, изменение инфраструктуры) агент **обязан** добавить в реестр запись:

- `[дата] Название решения` — краткое описание: что сделано, где (пути/сервисы), какое влияние и статус (`реализовано` / `в работе` / `отменено`).

Роадмэп собирается из записей реестра; для него использовать `docs/decisions/roadmap.md` — разделы: реализовано / в работе / планируется / идеи. Обновлять роадмэп по мере появления новых записей в реестре.
